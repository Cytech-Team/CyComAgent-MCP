# Remote Jobs VM Evidence Manifest Contract

## Status

Specification only. This file defines a future evidence format; it does not run tests, create a VM, or authorize execution. The manifest is not itself proof of containment. Evidence must be independently checked against the pinned runner, VM configuration, and guest image.

## Trust model

Evidence is divided into three classes:

- **Host-observed:** facts collected by the host runner without trusting guest-provided strings (VM process identity, configured machine type, attached devices, image and overlay digests, host-side start/stop/reset events, teardown verification).
- **Guest-trusted-channel:** facts emitted by a narrowly scoped trusted test agent over a channel that the tested payload cannot access or modify. This classification requires a documented isolation proof for that channel.
- **Guest-untrusted-log:** guest console, serial output, workload output, and any data that a tested payload could forge. Useful for diagnostics only; never sufficient alone for PASS.

A manifest must not upgrade guest-untrusted data to trusted based on a field supplied by the guest itself. The host runner assigns evidence source classifications.

## Required top-level structure

The representation is UTF-8 JSON. The producer emits deterministic compact JSON, while the verifier authenticates the exact received bytes rather than normalizing or reserializing them. Duplicate object keys, unknown fields, invalid UTF-8, non-finite numbers, excessive nesting, oversized strings, and oversized arrays are rejected. A parser must enforce byte and collection limits before allocating unbounded memory.

Required top-level members:

| Member | Meaning |
|---|---|
| schema_version | Exact manifest schema version |
| run_id | Host-generated unique opaque identifier |
| started_at_utc / finished_at_utc | RFC 3339 UTC timestamps |
| host | Host runner identity and version, without user/home path |
| vm | Configured and observed VM properties |
| guest | Guest kernel and platform facts |
| fixtures | Immutable test fixture metadata |
| cases | One result record for each scheduled case |
| host_events | Host-observed lifecycle/fault events |
| teardown | VM and overlay cleanup evidence |
| decision | Aggregate PASS, FAIL, or BLOCKED |

All identifiers are opaque and generated by the host runner. No username, home directory, production resource name, credential, raw environment value, or arbitrary filesystem path is allowed.

## Field contract

### host

Required fields: runner_id, runner_version, hypervisor, hypervisor_version, host_arch, host_kernel, isolation_profile_digest.

The runner ID is an opaque inventory identifier, not a hostname or account name. The isolation profile digest identifies the reviewed no-network/no-shared-host-resource VM configuration.

### vm

Required fields: machine_type, cpu_model, vcpu_count, memory_mib, image_sha256, overlay_id, network_devices, host_mounts, guest_agent_enabled.

For a qualifying run, network_devices and host_mounts must be empty and guest_agent_enabled must be false. A test that explicitly requires an exception needs a separately reviewed profile and cannot be represented as conforming to the default isolation profile.

### guest

Required fields: architecture, kernel_release, kernel_build_id, systemd_version, cgroup_mode, lsm, seccomp_available, mount_profile_digest.

The mount profile digest covers only the reviewed relevant mount facts; do not embed arbitrary host paths. Unsupported or unavailable facts are represented as null only where the schema explicitly permits it. Missing mandatory facts produce BLOCKED.

### fixtures

Each fixture has: fixture_id, kind, sha256, size_bytes, elf_class, elf_data, elf_machine, elf_type, expected_policy.

Only synthetic test fixtures are allowed. The fixture ID is opaque. A fixture record must not contain an executable path or raw binary. A non-ELF or script fixture may appear only in a negative test and must be marked as expected rejection.

### cases

Each case has: case_id, test_name, expected, observed, result, evidence, transitions.

- expected and observed are enumerated outcome codes, not free-form shell output.
- result is PASS, FAIL, or BLOCKED.
- evidence is a bounded list of records with source, kind, digest, and summary_code.
- transitions is an ordered list of state names and host/guest monotonic offsets where available.
- A case may be PASS only when every required assertion has sufficient trusted evidence and expected equals observed.
- Guest-untrusted-log evidence may explain a failure but cannot satisfy a PASS assertion.
- A missing case, missing evidence item, mismatch, timeout, or ambiguous outcome is FAIL or BLOCKED as defined before the run; never silently omit it.

### host_events

Each event has: event_id, event_type, host_monotonic_ns, case_id, actor, result. Event types are limited to VM_START, VM_PAUSE, VM_RESET, VM_POWER_OFF, VM_DESTROY, OVERLAY_DESTROY, WATCHDOG_TIMEOUT, and HOST_OBSERVATION. The actor is HOST_RUNNER. Guest claims cannot create host events.

### teardown

Required fields: vm_process_absent, overlay_absent, temporary_resources_absent, verified_by, evidence_digest.

All absence flags must be true for aggregate PASS. Verification must be host-observed. A guest message saying that cleanup succeeded is not acceptable evidence.

### decision

decision is PASS, FAIL, or BLOCKED. A PASS requires all scheduled cases PASS, all required platform facts present, host isolation preflight successful, teardown fully verified, and no unresolved evidence conflict. Any test failure yields FAIL. Missing runner capability or missing required evidence yields BLOCKED. A mixture of FAIL and BLOCKED yields FAIL because a known failure exists.

## Integrity and signing

The host runner serializes the canonical manifest, computes SHA-256 over the exact bytes, and signs that digest using a run-scoped host key that is not exposed to the guest. The signature envelope is stored separately from the manifest and includes the algorithm identifier, key identifier, digest, and signature bytes.

The guest must never receive the host signing key or a signing oracle. Guest-reported evidence is included as data, not signed as if it were host-observed. A signature proves which host runner emitted the manifest; it does not prove the truth of untrusted guest claims.

Canonicalization must be specified and tested before signing. Do not sign an in-memory map whose serialization can vary by key order or duplicate-key handling. The verifier must reject duplicate keys and recompute the digest from the exact canonical byte representation.

## Verification algorithm

1. Enforce maximum manifest size, nesting depth, string length, and array counts.
2. Parse strict UTF-8 JSON and reject duplicate/unknown keys.
3. Validate schema version and all enum values.
4. Verify the detached host signature and key validity for the run timestamp.
5. Verify the host runner identity and reviewed isolation profile digest.
6. Verify VM image, overlay, machine type, CPU, memory, attached devices, and host mounts from host-observed data.
7. Verify guest facts and classify each evidence source; do not trust guest-supplied classifications.
8. Check every scheduled test case exists exactly once and has the expected fixture digest.
9. Recompute each evidence digest and compare expected/observed result codes.
10. Verify ordered state transitions and host fault-event ordering against the test's declared expected recovery result.
11. Verify teardown from host-observed evidence.
12. Derive aggregate decision. Never accept the guest-provided aggregate decision without independently recomputing it.

## Anti-replay and correlation

A run ID is unique per host runner and run. Each case ID is unique within that run. Start-attempt IDs and child identities are opaque references; do not use PID alone as identity. Host events use monotonic time for ordering. UTC wall time is for human correlation only and must not decide event order.

A manifest from a previous run cannot satisfy a current run. The verifier checks the run ID, image/fixture digests, host runner key, and a host-generated nonce bound to the run. Reusing evidence or signatures across run IDs is rejected.

## Versioning

Schema changes are additive only within a minor schema version if the strict parser can still reject unknown fields safely. Any changed trust semantics, enum meaning, canonicalization, or required field increments the major schema version. Verifiers must fail closed on unsupported major versions.

## Acceptance

This contract is ready for implementation review only after independent review of the host runner trust boundary, signature key custody, canonical JSON rules, and the trusted guest evidence channel. Implementing a parser or signing utility does not authorize a VM run, payload execution, production service, or dispatch.

## 10. V1 implementation profile and unresolved schema decisions

The table above is a field contract, not yet a complete interoperable wire schema. An implementation must not guess missing enum values or infer absent fields. Before a verifier is merged, freeze the following V1 profile in code and tests:

- Set `schema_version` to the exact string `1.0`; reject every other value until an explicit migration exists.
- Add `run_nonce`, a host-generated cryptographically random value of at least 256 bits, and `test_plan_sha256`, the digest of the exact host-approved test plan. Both are required and are bound by the detached signature.
- The trusted test plan defines the complete expected case ID set, required evidence kinds and sources, expected outcome codes, transition order, and applicable platform requirements. A manifest cannot define its own required case set.
- Freeze closed enums for `fixture.kind`, `fixture.expected_policy`, `case.expected`, `case.observed`, `case.result`, `evidence.source`, `evidence.kind`, `evidence.summary_code`, transition names, host event types, and teardown verifier identity. Unknown values are rejected.
- Define `evidence.digest` as SHA-256 of the exact bounded evidence artifact bytes collected by the host. The manifest stores only the digest and a bounded summary code; it does not embed arbitrary guest output.
- Define `transitions` as strictly increasing per-case sequence numbers plus state enum and monotonic offset. Guest monotonic offsets are diagnostic only and cannot establish host event ordering.
- Define timestamp ordering and bounds: finished time cannot precede start time; host monotonic values cannot decrease; wall-clock timestamps never override monotonic ordering.
- Require exactly one case record for each case in the signed test plan, no duplicate IDs, and no unplanned cases.
- Require a non-empty evidence list for PASS cases. Every assertion in the plan must map to at least one evidence item from an allowed source; guest-untrusted-log can never satisfy an assertion.
- Require the host to derive the final decision from the signed plan plus host-observed evidence. The manifest's `decision` is a claimed result to compare, not an authority.
- Require `run_nonce` uniqueness in the host runner's protected run registry. Signature validity alone does not prevent replay of an old, correctly signed manifest.

### Exact-byte signature profile

To avoid an underspecified JSON canonicalization dependency, V1 signs the exact manifest byte sequence rather than a reserialized generic JSON map:

1. The producer builds the manifest from the V1 typed schema with deterministic field order and no map-typed fields.
2. The producer emits compact UTF-8 JSON using the Go standard encoder with HTML escaping disabled and no trailing newline.
3. The verifier rejects invalid UTF-8, duplicate keys, unknown fields, trailing values, and any schema-invalid representation. It does not normalize whitespace or reserialize before signature verification.
4. SHA-256 is computed over the exact received bytes. Ed25519 signs the 32-byte digest; the detached envelope identifies algorithm `Ed25519-SHA256`, trusted key ID, digest, and base64url signature.
5. The verifier checks the key ID against an out-of-band host-runner trust store. A key ID or public key supplied only inside the manifest is not trusted.
6. Key rotation and revocation are managed out of band. The verifier must fail closed if the signing key was not trusted at the run timestamp.

This profile deliberately avoids signing arbitrary JSON maps. If future implementations use another language, they must pass the same byte-level conformance vectors before they can produce accepted V1 manifests.

### Mandatory parser limits

V1 must enforce, before decoding into typed structs:

- Manifest bytes: at most 1 MiB.
- JSON nesting depth: at most 16.
- Object members: at most 64 per object.
- Array entries: at most 512 per array.
- String byte length: at most 4096.
- Fixtures: at most 64.
- Cases: at most 256.
- Evidence records: at most 32 per case.
- Transitions: at most 64 per case.
- Host events: at most 1024.

These are format ceilings, not a target for normal output. The approved test plan should set lower per-run limits where practical. Exceeding any limit is a hard rejection, never truncation.


## 11. Pure Go validation primitive status

The first implementation slice lives in internal/vmevidence:

- ValidateStrictJSON enforces the 1 MiB byte ceiling, UTF-8 validity, duplicate-key rejection, trailing-value rejection, and the documented nesting/object/array/string ceilings.
- VerifyDetachedSignature verifies SHA-256 over the exact supplied bytes and Ed25519 using a public key supplied by the caller from an out-of-band trust store.
- The package has no filesystem, process, network, VM, service, or dispatch capability.

This is deliberately **not yet a complete V1 manifest verifier**. It does not validate the typed manifest schema, trusted test plan, enum set, run nonce registry, evidence provenance, state-transition semantics, host-observed VM configuration, teardown, or aggregate PASS/FAIL/BLOCKED. Callers must not treat successful primitive validation or signature verification as a passing VM proof. Those checks remain separate implementation and review gates.


## 12. Typed V1 structural decoder status

The package internal/vmevidence now decodes the documented top-level and nested records into fixed Go structs, rejects unknown fields, and requires exact compact V1 typed re-encoding (HTML escaping disabled, no trailing newline). This also rejects omitted/null required scalar fields when their canonical typed representation differs.

The structural checks currently cover:

- Exact schema version, required identity/platform fields, lowercase SHA-256 hex fields, and a lowercase hexadecimal run nonce of at least 256 bits.
- Canonical RFC 3339 UTC timestamps and finished-at ordering.
- Non-zero VM CPU/memory and the default no-network/no-host-mount/no-guest-agent profile.
- Fixture/case/event collection ceilings, duplicate fixture/case/event identifiers, evidence digest shape, per-case evidence/transition ceilings, increasing transition sequence numbers, and non-decreasing host monotonic offsets.
- Host event actor identity and non-decreasing host event monotonic offsets.
- Teardown record shape and aggregate decision vocabulary.

This is still structural validation, not semantic proof. Closed enum allowlists and transition state-machine legality are intentionally not inferred from descriptive prose; they need a separately reviewed V1 enum/test-plan registry. In particular, a structurally valid manifest may claim PASS without sufficient evidence. No API in this package currently upgrades that claim to a verified PASS. The next gate is a trusted Test Plan model and independent decision derivation.

## 13. Trusted Test Plan and closed V1 vocabularies

The pure Go decoder accepts only a canonical compact V1 plan whose exact bytes pass detached Ed25519 signature verification against a caller-supplied out-of-band trust store. The decoded plan retains the exact byte digest privately; the independent evaluator requires the manifest test_plan_sha256 to match that digest. An unsigned plan cannot be passed off as trusted through this API.

The current closed vocabularies are:

- Fixture kind: ELF_STATIC, ELF_DYNAMIC, SCRIPT, NON_ELF.
- Fixture expected policy: ALLOW, REJECT.
- Case outcome: EXECUTED, REJECTED, TIMED_OUT, NOT_RUN, BLOCKED.
- Case result and aggregate decision: PASS, FAIL, BLOCKED.
- Evidence source: HOST_RUNNER, TRUSTED_GUEST_CHANNEL, GUEST_UNTRUSTED_LOG. The last source is diagnostic-only and forbidden in a trusted plan's allowed assertion sources.
- Evidence kind: HOST_VM_CONFIG, HOST_PROCESS_LIFECYCLE, HOST_TEARDOWN, HOST_ISOLATION, GUEST_KERNEL_FACTS, SYSCALL_RESULT, RESOURCE_LIMIT_RESULT, EXECUTION_RESULT, DIAGNOSTIC_LOG.
- Evidence summary: ASSERTION_MET, ASSERTION_FAILED, OBSERVATION_RECORDED, UNAVAILABLE, MISMATCH.
- Transition state: received, validated, reserved, child_gated, containment_confirmed, released, running, terminal, rejected, unknown.
- Host event: VM_START, VM_PAUSE, VM_RESET, VM_POWER_OFF, VM_DESTROY, OVERLAY_DESTROY, WATCHDOG_TIMEOUT, HOST_OBSERVATION.
- Teardown verifier identity: HOST_RUNNER.

The initial evaluator revalidates manifest structure, compares the exact planned case set, checks expected outcome and case result, requires each planned evidence kind from an allowed trusted source with ASSERTION_MET, checks required transitions as an ordered subsequence, checks plan platform requirements, requires the three core host lifecycle events (VM_START, VM_DESTROY, OVERLAY_DESTROY), and requires all teardown absence flags to be host-verified. The guest decision field is not used to derive the returned decision.

**Important remaining limitation:** evidence digests and source labels are not yet resolved to independently collected host artifact bytes or a protected host event journal. The evaluator is a pure policy calculation over already-decoded records; it does not prove that a signer was authorized for a particular runner, that a nonce is unique, or that claimed host observations actually occurred. Those require the protected host trust/nonce registry and evidence artifact verifier. A PASS from synthetic unit fixtures is only a unit-test result, never a real VM proof.

## 14. Trust-store and anti-replay interfaces

The pure package now defines two explicit host-owned boundaries:

- `TrustStore.LookupTrustedKey(keyID, purpose, at)` returns a copied Ed25519 public key only when the key is registered for the requested purpose and is inside its validity interval. Purposes are separated as `TEST_PLAN` and `MANIFEST`; a key trusted for one cannot automatically sign the other.
- `NonceReservationStore.ReserveRunNonce(runnerID, nonce, runID, reservedAt)` is an atomic reservation contract. A production implementation must be durable across process restart, concurrency-safe across all runner instances sharing the same replay domain, and fail closed when commit durability is uncertain.

`VerifyAndReserveManifest` verifies the detached manifest signature through the purpose-scoped trust store, decodes the canonical structural manifest, binds the runner identity from the verified payload, then requests one nonce reservation. Reservation happens before downstream evaluation; a later failed evaluation does not release the nonce. This intentionally prevents replaying a signed but unsuccessful run as a new attempt.

`MemoryTrustStore` and `MemoryNonceStore` exist only as test/reference implementations. They are process-local, non-durable, and explicitly unsuitable for production. The production trust authority, key rotation/revocation administration, durable transactional nonce database, retention/backup policy, cross-host uniqueness scope, and recovery procedure remain unimplemented. The interfaces alone do not provide persistence or protect themselves from a compromised host.

The manifest verifier does not yet prove evidence artifact bytes against a host journal. No production runner, VM lifecycle, dispatch, auto-repair, service, listener, or workload execution is introduced by these interfaces.

## 15. Anti-replay identity scope and durable-store implementation gate

The replay identity is the pair of independently unique values scoped to a runner: `(runner_id, run_nonce)` and `(runner_id, run_id)`. A nonce must not be reused for another run, and a run ID must not be reused with a fresh nonce. Different registered runners have independent namespaces unless a future deployment policy explicitly defines a shared global namespace.

The in-memory reference store now checks both indexes in one critical section. This closes the run-ID-reuse gap in the reference behavior, but it is still process-local and must not be represented as durable anti-replay protection.

A production persistence implementation is intentionally not selected yet. The repository has private Linux state-store primitives in the remote-jobs package, but importing that package into the evidence package would invert or couple package responsibilities. The module currently has no SQLite/Bolt persistence dependency. Before implementing a durable adapter, the architecture review must choose and approve:

- Storage engine and transaction model, including uniqueness constraints for both runner-scoped identities.
- State directory ownership, mode, symlink handling, descriptor pinning, lock scope, and cross-process behavior.
- Commit durability contract: data fsync, atomic commit/rename or database commit, parent-directory fsync where applicable, and fail-closed handling of uncertain commits.
- Crash recovery for incomplete writes and torn/corrupt records; corruption must never silently reset the replay registry.
- Backup/restore and rollback protection. Restoring an old backup must not make consumed nonces reusable; this likely requires an external monotonic checkpoint or an independently protected replay epoch.
- Key provisioning, rotation, revocation, validity-at-signing-time policy, and administrative authorization.
- Retention and privacy rules without deleting replay tombstones while signatures can still be replayed.

Until these decisions are approved and adversarially tested, only the interfaces and in-memory reference stores are available. No persistent database file has been created, no state path has been initialized, and no production trust authority has been provisioned.

## 16. Byte-level artifact verification boundary

The pure V1 artifact verifier accepts a decoded manifest and a caller-supplied map of exact artifact bytes keyed by lowercase SHA-256. It recomputes and checks:

- Every fixture digest and its declared byte length.
- Every case evidence digest.
- The teardown evidence digest.

Missing referenced bytes, digest mismatches, fixture size mismatches, unreferenced supplied artifacts, more than 2,048 artifacts, an artifact larger than 16 MiB, or more than 64 MiB of unique artifact bytes are rejected. Repeated references to the same digest are verified once. The verifier reads no paths, opens no files, and does not select an artifact source; the caller remains responsible for independently authorizing and safely reading the bytes.

A successful digest check proves only that the supplied bytes match the manifest's digest claims. It does not prove who created the bytes, when they were created, whether a host process actually observed the claimed event, whether the artifact came from an immutable host journal, or whether the artifact reader was compromised. In particular, evidence source labels remain claims until a separate host-journal and provenance verifier binds them to authenticated host observations. The byte verifier is not a VM runner, host journal, artifact collector, dispatch mechanism, or production trust authority.

## 17. Independently signed host event journal verification

The host event journal is a separate canonical JSON document with schema version, runner ID, run ID, run nonce, and the ordered host event records. It is authenticated using the distinct `HOST_JOURNAL` trust purpose; a key authorized only for `MANIFEST` or `TEST_PLAN` cannot authenticate a journal.

The pure verifier requires the journal identity tuple `(runner_id, run_id, run_nonce)` to equal the manifest identity, requires the exact same number of events, and compares every event field in order. It rejects unknown fields, duplicate event IDs, non-monotonic host timestamps, invalid actors/types, and a lifecycle that does not contain exactly one `VM_START`, followed by exactly one `VM_DESTROY`, followed by exactly one `OVERLAY_DESTROY`. This lifecycle ordering is a minimum structural condition, not proof that the host actually performed those operations.

The journal signature establishes that the corresponding trusted private key signed these exact journal bytes. It does not establish that the host kernel, runner process, signing key, clock source, or journal collector was uncompromised. A production design still needs protected append-only host collection, independent key custody, durable sequence/checkpoint protection against truncation and rollback, and a separately reviewed trust administration process. The current verifier reads caller-supplied bytes only; it does not create, persist, collect, or retrieve a journal and does not authorize VM execution or dispatch.

## 18. Journal chain integrity and rollback protection

Each signed `HostEventJournal` now carries `journal_sequence` and `previous_journal_sha256`. `VerifyHostEventJournalChain` accepts an explicit `HostJournalCheckpoint` and requires the incoming sequence to be exactly the checkpoint sequence plus one, and the predecessor digest to equal the checkpoint digest. On success it returns a next checkpoint containing the exact SHA-256 of the signed journal bytes.

This detects a skipped journal, replay of an already accepted journal, a fork from a different predecessor, and replacement of a journal while the verifier retains the newer checkpoint. The verifier is pure: it does not persist the returned checkpoint. The caller must update an independently protected checkpoint authority atomically with acceptance. A checkpoint kept beside the journal stream, or restored from the same backup as that stream, does not provide rollback protection. The initial genesis checkpoint (sequence zero and the agreed genesis digest) must itself be provisioned through an independent trust procedure.

The current chain is one signed journal document per sequence and binds that document to the complete Manifest host-event list. It does not implement a collector, append-only storage, checkpoint quorum, transactional persistence, key rotation, or recovery protocol. It therefore provides a verification primitive, not a production anti-rollback service. A compromised host or signing key can still sign false events and a fully consistent replacement chain; independent host observation and key custody remain separate requirements.

## 19. Independent checkpoint authority contract

`CheckpointAuthority` defines two operations: load the latest checkpoint for the exact `(runner_id, run_id, run_nonce)` identity, and `CompareAndAdvance(expected, next)`. The latter is a strict compare-and-swap contract: compare the complete checkpoint value and replace it with the next value in one atomic transaction. The next checkpoint must preserve the identity, increment sequence by exactly one, and advance the digest. Concurrent consumers of one predecessor must not both succeed.

`VerifyAndAdvanceHostEventJournalChain` composes load, signed-chain verification, and compare-and-advance. It does not retry a failed or uncertain commit. A production authority must make successful commits durable before returning, survive process restart, coordinate across processes/hosts, and fail closed on uncertain durability. If a commit result is uncertain, the caller must reload and reconcile the stored head before taking any further action; blindly retrying can obscure whether the first commit succeeded.

`MemoryCheckpointAuthority` is only a concurrency-safe reference implementation. Its mutex provides a single-process atomic CAS for tests; it is volatile and must not be used as an independent production checkpoint anchor. Genesis checkpoints must be provisioned through a separate trusted procedure. The interface does not choose a database, filesystem path, remote service, replication protocol, quorum, backup policy, or key administration mechanism. No persistent storage or production authority has been created.

Crash-consistency requirements for a future adapter include atomic compare-and-swap across all checkpoint fields, durable commit before success, recovery from torn/corrupt state without resetting to genesis, process and host crash tests around the commit boundary, concurrent cross-process writers, backup/restore rollback tests, and explicit reconciliation for unknown commit outcomes. The authority must be administered and backed up independently from the journal source; otherwise an attacker or operator able to roll back both can defeat truncation detection.

The reference tests now exercise the ambiguous-acknowledgement failure mode: a test authority commits the CAS successfully and then returns an injected error as if the acknowledgement were lost. The orchestration helper returns the error and does not retry. A subsequent independent read observes the advanced checkpoint, demonstrating the required caller reconciliation path. This is a deterministic fault-injection test of the interface contract, not a process-kill, power-loss, filesystem durability, database transaction, or production storage test.

A future durable adapter must additionally run subprocess/crash-injection tests at each storage boundary: before transaction start, after expected-head read, after write intent, during durable commit, after durable commit but before acknowledgement, and during recovery. Tests must prove that restart yields either the exact old head or exact new head, never a partial record, silent genesis reset, fork, or successful acknowledgement for a non-durable commit. Those tests cannot be meaningfully claimed until a storage engine and adapter are separately selected and approved.
